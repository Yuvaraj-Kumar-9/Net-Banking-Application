# HFDC Bank — Deployment Guide

> HFDC Bank is a fictional educational banking simulation, not a real financial
> institution. Do not use it to hold real money or real customer data.

## Status

The application has been built, tested and verified locally. It is **not publicly
deployed yet**, and no live URL is claimed in this repository. Follow this guide
when hosting credentials are available, then update the status in
[`../PROJECT_STATUS.md`](../PROJECT_STATUS.md) and the README only after the live
URL has been verified.

Two rules apply throughout:

1. **Never commit secrets.** Use the hosting provider's secret/environment store.
2. **Never paste passwords, API keys or database URLs into chat or issues.**

---

## 1. Deployment options

| Option | Services | Best for | Notes |
| --- | --- | --- | --- |
| **A. Single container** (recommended) | Render (Docker) + managed MySQL 8 | Portfolio/demo with one origin | React and API share a domain; cookies stay first-party |
| **B. Railway** | Railway Docker service + Railway MySQL | One-platform setup | Similar result, different dashboard |
| **C. Split frontend/backend** | Render/Railway API + Vercel/Netlify UI | Separate CDNs | Needs CORS and `SameSite=None; Secure` cookies |

The repository includes:

- `Dockerfile` — multi-stage build of React + Spring Boot, non-root runtime.
- `render.yaml` — Render Blueprint for option A.
- `.env.example` — every supported environment variable.

## 2. Option A — Render + managed MySQL 8

### 2.1 Provision MySQL 8

Render does not offer managed MySQL. Use a MySQL-compatible provider:

#### Aiven for MySQL (free plan)

1. Sign in at <https://console.aiven.io>.
2. **Create service → MySQL → Free plan**, choose a region close to your users.
3. Wait for the service state to become **Running**.
4. Open the service and copy the **Service URI** (host, port, user, password).
5. In the **Databases** tab, add a database named `hfdc_bank` (or use the
   provider console to run `CREATE DATABASE hfdc_bank`).
6. Keep TLS enabled; Aiven requires it.

JDBC URL shape:

```
jdbc:mysql://HOST:PORT/hfdc_bank?sslMode=REQUIRED&allowPublicKeyRetrieval=true&serverTimezone=UTC&characterEncoding=utf8
```

#### TiDB Cloud Serverless (MySQL compatible)

1. Sign in at <https://tidbcloud.com>, create a **Serverless** cluster.
2. Create a database named `hfdc_bank` (SQL console or CLI).
3. Copy the host, port, user and password; TLS is required.

```
jdbc:mysql://HOST:4000/hfdc_bank?sslMode=REQUIRED&serverTimezone=UTC&characterEncoding=utf8
```

#### Railway MySQL

1. Create a project, add **MySQL**.
2. Use the provided host, port, user, password and database.
3. For a public connection from Render, enable the public TCP proxy.

### 2.2 Load the schema

Create the database first (provider console or SQL), then run the schema and,
for a demo, the seed:

```bash
mysql --host=HOST --port=PORT --user=USER --password \
      --ssl-mode=REQUIRED hfdc_bank < sql/01_schema.sql

# DEMO ONLY - creates the documented demo accounts and history.
# Skip this for a clean deployment and register real test users via the UI.
mysql --host=HOST --port=PORT --user=USER --password \
      --ssl-mode=REQUIRED hfdc_bank < sql/02_seed.sql
```

Verify:

```bash
mysql --host=HOST --port=PORT --user=USER --password \
      --ssl-mode=REQUIRED hfdc_bank -e "SHOW TABLES; SELECT COUNT(*) FROM customers;"
```

Expected tables: `customers`, `accounts`, `transactions`, `transfers`,
`beneficiaries`, `password_resets`.

> The seed contains **public demo credentials**. Use it only for a portfolio demo,
> and never store real data in the same database.

### 2.3 Repository and source control

The project is already published at
<https://github.com/Yuvaraj-Kumar-9/Net-Banking-Application> on branch `main`
(remote `origin`). Render and Railway can connect to that repository directly;
no further Git setup is required.

If you fork or clone it elsewhere:

```bash
git clone https://github.com/Yuvaraj-Kumar-9/Net-Banking-Application.git
cd Net-Banking-Application
```

Before pushing changes:

- `git status` must not list `.env`, `target/`, `node_modules/`, logs or database
  files.
- Search for secrets: `git grep -nE "(password|secret|token)\s*[:=]"` and confirm
  only placeholders/dev defaults are present.
- `hfdc_user` / `change_me` and the local script JWT secret are **local dev
  defaults** and must be replaced in production. `JWT_SECRET` itself has no
  default: the application refuses to start without a 32+ byte value.

### 2.4 Create the Render service

1. Sign in at <https://render.com>.
2. **New → Blueprint**, connect the GitHub repository.
3. Render reads `render.yaml` and proposes one Docker web service, `hfdc-bank`.
4. Fill the secret environment variables when prompted:

| Variable | Value |
| --- | --- |
| `DB_URL` | Full JDBC URL from step 2.1 |
| `DB_USER` | Database user |
| `DB_PASSWORD` | Database password |
| `JWT_SECRET` | Auto-generated by Render (`generateValue: true`) |
| `DEV_MODE` | `false` |
| `COOKIE_SECURE` | `true` |
| `COOKIE_SAME_SITE` | `lax` |

5. Apply/deploy. The first Docker build takes several minutes (Node build,
   Maven dependency download, jar packaging).
6. Render runs the health check `GET /api/auth/health`. A healthy deploy returns
   `{"status":"UP", ...}`.

If you prefer a manual web service instead of the Blueprint:

- **New → Web Service → Docker**, repository root, `Dockerfile` path.
- Health check path: `/api/auth/health`.
- Add the same environment variables.

### 2.5 Verify the live deployment

Replace `<app>` with the Render URL:

```bash
curl -i https://<app>.onrender.com/api/auth/health
curl -I https://<app>.onrender.com/
```

Checklist:

- [ ] Landing page loads and shows the simulation disclaimer.
- [ ] `/login` and `/dashboard` load (client-side routing works).
- [ ] Browser devtools show `hfdc_token` as **HttpOnly** and **Secure**.
- [ ] Demo login works (if seed was loaded).
- [ ] Dashboard figures come from the database, not hardcoded values.
- [ ] Deposit, withdrawal and transfer work.
- [ ] A mutating request without `X-XSRF-TOKEN` returns `403`.
- [ ] `GET /api/auth/me` without a cookie returns `401`.
- [ ] `GET /api/does-not-exist` (signed in) returns JSON `404`.
- [ ] Swagger UI is reachable at `/swagger-ui.html`.
- [ ] The page is usable at mobile width.

Only after these pass should you record the live URL in the README and
`PROJECT_STATUS.md`.

### 2.6 Post-deployment hardening

- Set `DEV_MODE=false` so reset tokens are never returned to the browser.
- Set `COOKIE_SECURE=true` (HTTPS only) and `COOKIE_SAME_SITE=lax` for same-origin.
- Rotate `JWT_SECRET`; rotating it invalidates all sessions.
- If the seed was loaded, treat the demo accounts as public. For anything beyond
  a demo, start from an empty database.
- Create a least-privilege database user for the app:
  `SELECT, INSERT, UPDATE, DELETE` on `hfdc_bank.*` only. Run schema migrations
  with a separate admin user.
- Enable provider backups and point-in-time recovery if available.
- Add rate limiting/CAPTCHA at the edge (Cloudflare, Render proxy or a gateway)
  for `/api/auth/login`, `/api/auth/forgot-password` and PIN endpoints.
- Restrict `CORS_ALLOWED_ORIGINS` to the real frontend origin if you split the
  deployment; same-origin needs no CORS.
- Configure a custom domain and force HTTPS.
- Add uptime monitoring against `/api/auth/health`.

## 3. Option B — Railway

1. Push the repository to GitHub.
2. In <https://railway.app>, **New Project → Deploy from GitHub repo**.
3. Railway detects the `Dockerfile` and builds the image.
4. **New → Database → MySQL** in the same project.
5. Add the backend variables:
   - `DB_URL=jdbc:mysql://HOST:PORT/hfdc_bank?sslMode=REQUIRED&serverTimezone=UTC&characterEncoding=utf8`
   - `DB_USER`, `DB_PASSWORD`
   - `JWT_SECRET` (long random value)
   - `DEV_MODE=false`, `COOKIE_SECURE=true`, `COOKIE_SAME_SITE=lax`
6. Expose the service on port `8080` (Railway injects `PORT`; the app honours it).
7. Load the schema/seed with the MySQL CLI or Railway's query console.
8. Set the health check to `/api/auth/health`.
9. Generate a public domain and run the verification checklist from section 2.5.

## 4. Option C — split frontend and backend

Use this only if you need a separate CDN for the UI.

### Backend

Deploy the API as in option A, but without the frontend in the jar. You can build
with Maven and run the jar on any Java host, or use the same Docker image (the UI
being present is harmless).

Set:

```
CORS_ALLOWED_ORIGINS=https://app.example.com
COOKIE_SECURE=true
COOKIE_SAME_SITE=none
DEV_MODE=false
```

### Frontend

Deploy `frontend/` to Vercel/Netlify with:

```
VITE_API_URL=https://api.example.com/api
```

Build command: `npm ci && npm run build`
Output directory: `dist`

### Caveats

- The auth cookie becomes third-party. Modern browsers (especially Safari) may
  block third-party cookies, breaking login.
- `SameSite=None` **requires** `Secure` and HTTPS.
- CORS must allow the exact frontend origin and credentials.
- Same-origin (option A) avoids all of these issues and is recommended.

## 5. Local Docker

Docker is **not installed** in the environment where this project was developed,
so the image has not been built locally. The Dockerfile is a standard multi-stage
build and is used by Render/Railway.

```bash
docker build -t hfdc-bank .

docker run --rm -p 8080:8080 \
  -e DB_URL="jdbc:mysql://host.docker.internal:3306/hfdc_bank?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC&characterEncoding=utf8" \
  -e DB_USER=hfdc_user \
  -e DB_PASSWORD=change_me \
  -e JWT_SECRET="replace-with-a-long-random-secret-at-least-32-characters" \
  -e DEV_MODE=false \
  -e COOKIE_SECURE=false \
  hfdc-bank
```

Open <http://localhost:8080>. `COOKIE_SECURE=false` is required for plain HTTP on
localhost; use `true` behind HTTPS.

To inspect the image without running it:

```bash
docker build -t hfdc-bank .
docker run --rm hfdc-bank java -version
```

## 6. Environment variables

| Variable | Required | Default | Production guidance |
| --- | --- | --- | --- |
| `PORT` | No | `8080` | Injected by most platforms |
| `DB_URL` | **Yes** | local MySQL URL | Include TLS (`sslMode=REQUIRED`) |
| `DB_USER` | **Yes** | — | Least-privilege app user |
| `DB_PASSWORD` | **Yes** | — | From the secret store |
| `JWT_SECRET` | **Yes** | — | 32+ random bytes; startup fails if missing/weak |
| `JWT_EXPIRATION_MS` | No | `86400000` | 1 day; shorten for higher security |
| `CORS_ALLOWED_ORIGINS` | No | localhost origins | Exact frontend origin if split |
| `COOKIE_SECURE` | No | `false` | **`true`** on HTTPS |
| `COOKIE_SAME_SITE` | No | `lax` | `lax` same-origin; `none` only for split + Secure |
| `DEV_MODE` | No | `true` | **`false`** in production |

Frontend build-time variable:

| Variable | Default | Notes |
| --- | --- | --- |
| `VITE_API_URL` | `/api` | Set to the API URL only for a split deployment |

Generate a JWT secret:

```bash
openssl rand -base64 48
```

## 7. Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Health check fails / 502 | App cannot start or DB unreachable | Check Render logs; verify `DB_URL`, TLS mode and firewall |
| `Communications link failure` | Wrong host/port or TLS required | Use the provider's public host and `sslMode=REQUIRED` |
| `Public Key Retrieval is not allowed` | MySQL `caching_sha2_password` over non-TLS | Add `allowPublicKeyRetrieval=true` (with TLS) |
| Login succeeds but next request is 401 | Cookie not sent | Same-origin recommended; check `Secure`, `SameSite`, HTTPS |
| `403 CSRF token missing or invalid` | Missing `X-XSRF-TOKEN` header | Ensure the SPA fetched `/auth/csrf`; check cookie domain |
| CORS error | Split deployment misconfigured | Set `CORS_ALLOWED_ORIGINS` exactly; allow credentials |
| 404 on `/dashboard` refresh | SPA fallback not active | Confirm the UI was copied into the jar (`static/index.html`) |
| Swagger 404 | Wrong path | Use `/swagger-ui.html` or `/swagger-ui/index.html` |
| Slow first request | Free tier cold start | Expected on free plans; upgrade or keep-alive |
| Demo login fails | Seed not loaded or DB reset | Run `sql/02_seed.sql` against the deployed database |

Useful commands:

```bash
# App health
curl -i https://<app>/api/auth/health

# Check the served SPA
curl -s https://<app>/ | head

# Follow Render logs
# Dashboard → service → Logs (or the Render CLI)
```

## 8. Rollback

1. In Render/Railway, redeploy the previous successful image or commit.
2. Rotate `JWT_SECRET` if you suspect session compromise; all users must log in
   again.
3. Restore the database from the provider's backup if a migration caused damage.
4. Re-run the section 2.5 checklist after rollback.

---

## 9. Cost and limitations

- Render free web services spin down after inactivity; the first request is slow.
- Free MySQL plans have storage/connection limits and may sleep.
- The Docker build downloads Node and Maven dependencies; the first deploy is the
  slowest.
- No email provider is configured, so production password reset requires adding
  one (the dev token is hidden when `DEV_MODE=false`).
- No built-in rate limiting, WAF or DDoS protection; put these at the edge before
  exposing the app publicly.
